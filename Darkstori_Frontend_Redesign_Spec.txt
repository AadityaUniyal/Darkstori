The execution is what's reading as generic. Section 0 explains exactly why,
with evidence from your own files.

--------------------------------------------------------------------------------
0. ROOT CAUSE — WHY THE CURRENT UI READS AS GENERIC
--------------------------------------------------------------------------------

Your theme.css names its colors after Indian cultural motifs — saffron,
peacock, monsoon, spice. That's the right instinct. But check the actual hex
values you assigned to them:

    --saffron-500:  #f97316   <- this is unmodified Tailwind "orange-500"
    --peacock-500:  #0ea5e9   <- this is unmodified Tailwind "sky-500"
    --monsoon-500:  #10b981   <- this is unmodified Tailwind "emerald-500"
    --spice-500:    #ef4444   <- this is unmodified Tailwind "red-500"

The names promise a specific cultural identity. The values are the exact
same defaults every Tailwind dashboard on the internet ships with. That
mismatch is the entire problem in one finding: visually, this looks like
any other dark-mode SaaS dashboard, because the actual pixels ARE any other
dark-mode SaaS dashboard. The fix below is not "redesign everything" — it's
"make the colors actually be what their names promise."

Same pattern in typography: Inter (body) + Poppins (heading) is one of the
single most common pairings in AI-generated and template dashboards. Nothing
wrong with Inter as a workhorse, but Poppins-as-display-face is a tell.

The good news: RangoliLoader already exists in your component list. That
tells me someone on this project already had the right instinct (a real
Indian visual motif, not a generic spinner) but it's currently an isolated
component instead of a running theme. Section 2 turns it into the page's
actual signature element instead of a one-off.

2. SIGNATURE ELEMENT — THE RANGOLI MOTIF, MADE STRUCTURAL
--------------------------------------------------------------------------------

You already built RangoliLoader. Don't let it be the only place this idea
shows up. A rangoli is a radial, symmetric pattern — which happens to be the
exact geometry you need for THREE real functional pieces of this product,
not just a loading spinner:

  a) Opportunity Score gauges (Neighborhoods, Dashboard "Top Opportunities")
     Currently these are presumably plain numbers or bars. Render them as a
     radial rangoli-segment gauge: a circular ring divided into 8 or 12
     petal-like segments (rangoli petal count), filled clockwise based on
     score (0-10). Center shows the number in font-mono. Color: saffron at
     low fill, marigold mid, monsoon at high (8.0+ = "this is a strong
     opportunity" = green).

  b) Coverage Score rings (Analytics, Neighborhoods)
     Same radial treatment, 0-100 scale, peacock-to-monsoon gradient.

  c) The loading state (RangoliLoader, already built) — extend its existing
     pattern so its geometry visually matches (a) and (b). Right now if it's
     a generic rotating rangoli, make the segment count and proportions the
     same as the gauges, so a user subconsciously recognizes "this shape =
     this product" across loading, scoring, and coverage contexts.

This is the one piece of "boldness" this redesign spends — keep everything
else (cards, tables, charts) quiet and disciplined around it, per design
best practice: one signature, not five competing ideas.

Secondary, smaller motif: live order pings on the map (see Section 4) ripple
outward like rain on a stepwell tank rather than a generic Uber-style pulsing
dot — slower, concentric, fading rings instead of a single scale+fade pulse.

NAVBAR (components/Navbar.jsx)

  - Center-right: CitySelector component — render as a pill-shaped dropdown

  - Right: notification bell icon (lucide-react, already a dependency),
    user avatar circle (initials on saffron-100 background, saffron-600
    text), logout as a dropdown item not a separate visible button.

SIDEBAR (components/Sidebar.jsx)
  - Width: 240px expanded / 72px collapsed (icon-only). Collapse toggle at
    the bottom, not the top — top is reserved for the most-used nav items.
  - Nav order (most-used first, per your own route list):
      Dashboard, Analytics, Forecast, Neighborhoods, Simulator,
      AlgorithmLab, ResilienceCockpit
  - Active route: left border 3px solid saffron-500, background
    saffron-100, icon and label switch from text-secondary to
    text-primary. No other route gets any accent color — only one active
    state should ever be visible at once.
  - Icons: lucide-react, 18px, consistent stroke-width 1.75 across every
    icon in the app (mismatched stroke widths between icons is a common
    "off" tell — audit this).
  - Hover (non-active item): background var(--color-surface), no color
    change, 150ms transition (--transition-fast).

BUTTONS (define once as a class system, reuse everywhere)
  - Primary: background saffron-500, text #0B0D14 (dark text on bright
    button reads more premium than white-on-orange), radius-md, weight 600,
    padding space-3 / space-5. Hover: saffron-600, translateY(-1px), shadow
    shadow-md. Active: translateY(0), shadow-sm.
  - Secondary: transparent background, 1px border color-border, text
    text-primary. Hover: border peacock-500, no fill change — restrained.
  - Destructive (e.g. "Delete simulation," "Remove store"): transparent
    default, spice-500 text + border. Hover: spice-500 fill, white text.
  - Icon-only buttons (map controls, table row actions): 32px square,
    radius-md, background transparent, hover background color-surface.
  - All buttons: disabled state = opacity 0.4, cursor not-allowed, no hover
    transform. Loading state = same size, spinner replaces label text (never
    shrink/grow a button when it goes into a loading state — causes layout
    shift).

CARDS (AnimatedCard.jsx — give it one consistent treatment)
  - background var(--color-bg-card), border 1px var(--color-border),
    radius-lg, padding space-6.
  - Entrance: handled by StaggerChildren — fade + translateY(8px), 80ms
    stagger between siblings, NOT more than 80ms or the dashboard feels
    slow to settle on load.
  - Hover (only for clickable/navigable cards, e.g. "Top Opportunity" row
    items): border color shifts to saffron-500 at 30% opacity, translateY
    (-2px), shadow-md. Static info cards (KPI tiles) get NO hover effect —
    hover states should only ever imply "this is interactive."

EMPTY / ERROR STATES (ErrorBoundary.jsx + per-page empty states)
  Per the interface-writing principle: explain what happened and what to do,
  in the product's voice, never apologize, never be vague.
  - Empty (e.g. no stores in this city yet): icon (outline, muted), one line
    — "No stores mapped in [city] yet." — one action button if applicable:
    "Add a store" / "Switch city."
  - Error (API failure — note Dashboard.jsx already has a FALLBACK_METRICS
    pattern, which is good defensive design): when falling back to mock
    data, show a small, dismissible inline banner — "Showing sample data —
    live metrics unavailable" — peacock-100 background, peacock-500 left
    border, NOT a full-page error. Never silently show fallback data without
    indicating it's fallback data; a user making a decision off it needs to
    know.
  - 404 (NotFound.jsx): keep it simple — no illustration needed. Big
    font-display "404," one line in font-body ("This page doesn't exist."),
    one primary button back to Dashboard. Resist the urge to make this page
    cute; it's the one screen where restraint matters most.

4. MAP DESIGN SYSTEM (applies to MapView.jsx — Leaflet + Deck.gl layers)
--------------------------------------------------------------------------------

BASEMAP
  - Do not use Leaflet's default OpenStreetMap tile style — it's bright,
    busy, and clashes with a dark UI. Use CARTO's "Dark Matter" basemap
    tiles (free, no key required, built exactly for this use case:
    https://carto.com/basemaps) or a custom Mapbox dark style if you already
    have a Mapbox token elsewhere in the stack.
  - Reduce label density on the basemap itself (most dark basemap providers
    have a "no labels" variant) and render your OWN city/area labels in
    font-display so typography stays consistent with the rest of the app
    instead of inheriting the basemap's default label font.

MARKERS (individual dark stores)
  - Replace default Leaflet pin markers with a small solid circle (10px),
    color-coded by status:
      active store      -> peacock-500
      opportunity zone   -> marigold-500
      saturated/competitor -> spice-500 at 60% opacity
  - On hover: circle scales to 14px (150ms), thin saffron-500 ring appears
    around it (2px, offset 3px) — do this with CSS transform, not by
    re-rendering the marker, to keep map interaction smooth at scale.

CLUSTERING (leaflet.markercluster — already a dependency)
  - Cluster icon: circular, background color-bg-card at 90% opacity, border
    1px saffron-500, count in font-mono, white text. Avoid the
    library's default green/yellow/orange size-tiered clusters — that's the
    single most recognizable "default Leaflet" tell. Use ONE consistent
    cluster color regardless of count; let the number, not the color,
    communicate density.

HEATMAP LAYER (SLAHeatmap.jsx, Deck.gl HeatmapLayer or similar)
  - Color ramp: peacock-500 (low) -> marigold-500 (mid) -> spice-500 (high).
    This is a deliberate departure from the generic blue-to-red heatmap
    ramp most tools ship with — same general "cool to hot" logic, but using
    your actual palette instead of a rainbow default.
  - Opacity: cap at 0.75 max even at peak intensity — a fully opaque heatmap
    layer obscures the basemap underneath and makes the map feel cluttered
    rather than informative.

LIVE ORDER PINGS (LiveTracker.jsx)
  - Per Section 2: concentric expanding rings (3 rings, staggered start,
    1.8s duration each, ease-out), saffron-500 stroke fading to 0 opacity,
    NOT a single scale-and-fade dot. This is slower and calmer than a typical
    "live" pulse — appropriate for a planning/intelligence tool, not a
    real-time gaming UI.

POPUPS / TOOLTIPS
  - Dark background matching color-bg-card, NOT Leaflet's default white
    popup box (this is the second most common "default Leaflet" tell after
    the cluster colors). Radius-md, border color-border, small triangle
    pointer in the same dark color.
  - Content hierarchy inside popup: store/area name in font-display 1rem,
    2-3 key stats below in font-mono with text-secondary labels, one action
    link ("View details") in peacock-500.

LEGEND
  - Persistent, bottom-left, small card matching the popup styling. Always
    visible when a color-coded layer (heatmap, status markers) is active —
    never make a user guess what a color means on a map this data-dense.

MAP CONTROLS
  - Zoom controls: custom-styled to match icon-only buttons (Section 3), NOT
    Leaflet's default blue-bordered zoom buttons.
  - Layer toggle (heatmap on/off, cluster on/off, etc.): small pill toggle
    group, top-right of the map, matching the CitySelector pill style for
    visual consistency across the app.

5.1 LOGIN (pages/Login.jsx)
--------------------------------------------------------------------------------
JOB: get a returning user into the product in under 10 seconds. Nothing on
this page should compete with that.

LAYOUT: centered card, max-width 420px, vertically centered. Background:
AmbientBackground component (already exists) — use it here specifically:
a very slow, very subtle drifting rangoli-pattern watermark at 4-6% opacity,
large scale, slow rotation (90s+ per rotation). This is the one place a
decorative motif earns its keep purely on first impression.

CARD CONTENTS, top to bottom:
  1. Wordmark + small tagline directly under it in text-secondary, font-
     body, 0.875rem: "Quick-commerce intelligence for India's dark stores."
     (Specific, says what the product does, not a generic "Welcome back.")
  2. Email field — label "Email," placeholder "you@company.com," icon
     (mail, lucide-react) inline left.
  3. Password field — label "Password," icon (lock), show/hide toggle icon
     on the right (eye / eye-off), NOT a separate checkbox below the field.
  4. Row: "Remember me" checkbox (left) + "Forgot password?" link in
     peacock-500 (right).
  5. Primary button, full width: "Sign in" (NOT "Submit" or "Login" — name
     the action, not the mechanism).
  6. Below the card, outside the border: "Don't have an account? Create
     one" — secondary link, text-muted with peacock-500 on the action word
     only.

STATES:
  - Validation error (wrong password): inline below the field, spice-500
    text, small lock-shake animation on the field border (translateX
    -4/4/-4/0px, 300ms total) — NOT a full-page red banner.
  - Loading: button shows spinner replacing "Sign in" text, same button
    width (no layout shift), disabled state on both fields.
  - Success: brief checkmark animation in the button (200ms) before the
    route transition fires — gives the action a felt sense of completion
    instead of an instant, jarring redirect.

ANIMATION: card enters with fade + translateY(12px), 400ms, ease matching
--transition-base. No staggered field-by-field entrance here — that's a
common over-animation mistake; the login card should feel immediate, not
choreographed.

5.2 DASHBOARD (pages/Dashboard.jsx)
--------------------------------------------------------------------------------
JOB: answer "how is the business doing right now, across all cities" in one
glance, then let the user drill into whatever looks interesting.

Confirmed real data shape from your code: summary (total_stores,
total_neighborhoods, total_orders_30d, total_competitive_moves),
city_overview (per-city store/neighborhood/opportunity), top_opportunities,
sentiment (per platform), recent_competitive_moves.

LAYOUT (top to bottom):

  ROW 1 — Summary strip (4 KPI cards, AnimatedCard + AnimatedCounter)
    Each card: icon top-left (you already import TrendingUp, MapPin,
    Building2, Zap, Star — good, keep these, one distinct icon per metric),
    big number in font-display using AnimatedCounter (count up from 0 over
    800ms on first load only, NOT on every refetch — re-triggering the
    count-up every 5-minute poll interval will feel glitchy and cheap),
    label below in text-secondary, small delta indicator (+/- vs last
    period) in monsoon-500 or spice-500.

  ROW 2 — Map + City Pulse, side by side (60/40 split on desktop, stacked
    on tablet/mobile)
    Left: MapView, showing all active stores across all cities (status-
    colored markers per Section 4), default zoom fit to all markers.
    Right: CityPulse component — render as a vertical list of cities
    (using city_overview data), each row showing the rangoli-style
    opportunity-score gauge (Section 2) at small size (32px), city name,
    store_count + neighborhood_count in font-mono. Sort by
    avg_opportunity_score descending — surface the best opportunity first,
    not alphabetically.

  ROW 3 — Top Opportunities (table or card-grid using top_opportunities)
    Card-grid, 3 columns desktop, each card: neighborhood_name (font-
    display, 1rem), city as a small peacock-500 pill tag, opportunity_score
    as the rangoli gauge (Section 2, this time at full size ~64px). Clicking
    a card navigates to Neighborhoods filtered to that area — this is a
    primary interaction, so the whole card should be clickable with the
    hover treatment from Section 3, not just a small "view" link.

  ROW 4 — Sentiment by Platform (using sentiment data: platform,
  positive_pct, negative_pct, avg_sentiment)
    Horizontal stacked bar per platform (Instamart, Zepto, Blinkit, Swiggy
    Genie) — positive segment in monsoon-500, negative in spice-500, a thin
    neutral segment in text-muted for the remainder. Platform name left-
    aligned in font-body, avg_sentiment shown as a small number to the
    right in font-mono. This is real comparative data — a stacked bar
    communicates it far faster than four separate donut charts (a common
    over-engineered default for this kind of data).

  ROW 5 — Recent Competitive Moves (using recent_competitive_moves.moves)
    Vertical timeline/feed, most recent first. Each entry: platform name as
    a small colored tag (assign each platform ONE consistent color used
    everywhere it appears in the app — Blinkit, Zepto, Instamart, Swiggy
    Genie should each always render in the same color, building visual
    vocabulary across pages), description text in font-body, impact_level
    as a small dot — your existing IMPACT_COLOR mapping (HIGH/MEDIUM/LOW)
    is fine logically; just move those three colors onto the actual palette
    (HIGH -> spice-500, MEDIUM -> marigold-500, LOW -> monsoon-500) instead
    of the current pink/yellow/green (#fa709a/#f6d365/#43e97b) which, like
    the theme colors, are off-palette and read as a different design system
    bolted onto this one.

EMPTY/FALLBACK: Dashboard.jsx already has FALLBACK_METRICS for resilience —
good defensive engineering. Per Section 3, when this fallback is active,
show the inline "Showing sample data" banner; don't let it be invisible.

ANIMATION: StaggerChildren across the 4 KPI cards on load (80ms stagger).
Map and below-the-fold rows fade in on scroll (Framer Motion
whileInView), not all at once on page load — a dashboard with this many
sections animating simultaneously on load reads as chaotic.

5.3 ANALYTICS (pages/Analytics.jsx)
--------------------------------------------------------------------------------
JOB: let a user understand coverage gaps at the PIN-code level (backed by
GET /api/analytics/coverage).

LAYOUT:
  - Top: filter bar — city dropdown, PIN code search (font-mono input,

  - Right 40%: ranked list of worst-covered PIN codes, each row clickable

    ease-in-out — Leaflet's flyTo supports this natively).
  - Below the fold: a trend chart (Recharts line chart) of overall coverage
    % over time, monsoon-500 line, subtle area fill at 8% opacity beneath
    it.

5.4 FORECAST (pages/Forecast.jsx — "Predictions")
--------------------------------------------------------------------------------
JOB: let a user request a demand forecast for a PIN code and trust the
result (backed by POST /api/predictions/demand).

LAYOUT:
  - Left panel (form, ~30% width): PIN code input (font-mono), days-ahead
    selector (segmented control: 7 / 30 / 90 — match your API's existing
    "days" parameter), primary button "Run forecast."
  - Right panel (~70%): result area.
    - Before a forecast is run: empty state per Section 3 — "Enter a PIN
      code to see a demand forecast." Don't show an empty chart frame; show
      nothing until there's something to show.
    - After: a line chart with a SHADED CONFIDENCE BAND, not just a single
      line. Your backend test (test_prediction.py) confirms the API
      returns lower_bound / prediction / upper_bound — surface all three.
      Center line in saffron-500, confidence band in saffron-100 at 20%
      opacity. This single visual choice (showing the uncertainty range,
      not just a point estimate) is the most important integrity signal on
      this entire page — never render a forecast as if it were a fact.
    - Below the chart: the actual numeric metrics this forecast's model
      was validated against (R², MAPE — once real, per your data work) in
      small font-mono text, so the page itself communicates "this is a
      modeled estimate with known error bounds," not a black-box number.

ANIMATION: chart line draws in left-to-right (Recharts supports animated
stroke-dashoffset reveal), 600ms, on result arrival only.

5.6 SIMULATOR (pages/Simulator.jsx)
--------------------------------------------------------------------------------
JOB: let a user test "what if we placed a store here" before committing —
this is your most interactive, highest-value page; treat it as the
product's second signature moment after the map itself.

LAYOUT:
  - Full-width map, with an explicit "placement mode" toggle button (top
    of map, secondary button style). When active, clicking anywhere on the
    map drops a draft marker (dashed outline, marigold-500, distinct from
    the solid real-store markers in Section 4 — a draft must never be
    visually confusable with a real, committed store).
  - On drop: a side panel slides in from the right (Framer Motion, 300ms,
    ease matching --transition-base) showing real-time computed metrics
    for that point: estimated demand_score, competition_gap,
    logistics_viability, recommended_store_size_sqft, estimated_breakeven
    _months, confidence — these are real fields confirmed in your
    placement.py route. Render confidence explicitly (e.g. "62% confidence"
    in font-mono next to the headline number) so a low-confidence
    simulation never reads with the same authority as a high-confidence one.
  - "Save this simulation" secondary button, "Clear" destructive-style
    button (per Section 3's destructive button spec) to remove the draft
    marker and start over.
  - Comparison mode: allow 2-3 draft markers active at once, side panel
    becomes a comparison table instead of a single card — this is the
    actual decision-making moment ("should we place it here or here") and
    deserves direct support, not a one-at-a-time workflow.

    generic "Feature 1, Feature 2").
  - Experiment comparison: if comparing 2+ runs, render their metrics
    side-by-side in font-mono columns, with the better value in each row
    highlighted (monsoon-500 text) — this page is for someone making a
    "which model do we ship" decision, so the comparison itself should be
    doing visual work, not just listing numbers.
  - This page should NOT use the rangoli gauge motif — that motif is for
    business-facing opportunity/coverage scores. Keep AlgorithmLab visually
    closer to a clean data table / Grafana-style density. Mixing the two
    visual languages on the wrong page is how a design system falls apart.

5.8 RESILIENCE COCKPIT (pages/ResilienceCockpit.jsx)
--------------------------------------------------------------------------------
JOB: this name plus your backend's alert_manager.py and performance_
monitor.py strongly suggests this is an ops/monitoring page — system health,
not business analytics. Design it accordingly: faster-updating, more alert-
oriented, less exploratory.

LAYOUT:
  - Top: system status strip — overall status (Operational / Degraded /
    Critical) as a single, large, unmissable indicator, color-coded
    (monsoon/marigold/spice), left-aligned, font-display.
  - Active alerts feed: each alert as a card with severity-colored left
    border (matching the 3-tier severity colors used in Dashboard's
    competitive moves, for consistency), timestamp in font-mono, a "View
    affected area" link that flies the map (if relevant) or links to the
    affected model in AlgorithmLab (for drift alerts).
  - Drift detection panel: if a model's drift score crosses a threshold,
    surface it here explicitly with the threshold value shown alongside
    the actual value (e.g. "MAPE drift: 18.2% — threshold 15%") — always
    show the threshold next to the breach, never just "alert fired" with
    no context for why.
  - This page should refresh more aggressively than Dashboard (consider a
    shorter poll interval, e.g. 30-60s vs Dashboard's 5 minutes) since its
    entire job is "tell me the moment something's wrong."

6. ANIMATION CATALOG (consolidated — use these as the ONLY motion patterns
   in the app; resist inventing a new easing curve or duration per page)
--------------------------------------------------------------------------------

  Page transition (App.jsx already has this — keep it, it's good):
    fade + translateY(16px) + scale(0.98) -> identity, 350ms,
    cubic-bezier(0.16, 1, 0.3, 1) on enter; faster (200ms, ease-in) on exit.

  Card/list entrance (StaggerChildren):
    fade + translateY(8px), 80ms stagger, never more than ~6 siblings
    staggered in one group — beyond that, switch to a simultaneous fade
    instead of compounding the delay.

  Counter count-up (AnimatedCounter):
    800ms, ease-out, triggers ONLY on first mount per session — not on
    every poll refetch.

  Hover lift (interactive cards, Section 3):
    translateY(-2px) + shadow-md, 150ms (--transition-fast). Reverse on
    mouse-leave at the same duration — asymmetric hover timing (fast in,
    slow out) feels unresponsive.

  Map flyTo (Leaflet):
    600ms, ease-in-out, used when a user clicks a list item that
    corresponds to a map location (Analytics worst-coverage list, Dashboard
    opportunity cards).

  Live order ping (LiveTracker, Section 2):
    3 concentric rings, staggered 200ms apart, each ring 1.8s duration,
    ease-out, opacity 0.6 -> 0.

  Loading (RangoliLoader):
    continuous rotation, 6-8s per full rotation — slow enough to read as
    "processing," not "broken/spinning forever."

  Reduced motion: every animation above must respect
  prefers-reduced-motion — fall back to a simple opacity fade (150ms) with
  no transform, no exceptions, including the rangoli loader (fall back to
  a static rangoli icon with a subtle opacity pulse instead of rotation).

--------------------------------------------------------------------------------
7. RESPONSIVE & ACCESSIBILITY NOTES
--------------------------------------------------------------------------------

  - Sidebar collapses to icon-only automatically below 1024px, to a bottom
    tab bar (5 most-used routes) below 640px — don't just shrink the
    existing sidebar, the interaction model should change at that
    breakpoint.
  - Map + side-panel layouts (Analytics, Simulator) stack vertically below
    1024px, map on top at 50vh height, panel below — never let the map
    shrink below a usable height to preserve a side panel's width.
  - Every interactive element needs a visible keyboard focus ring —
    2px solid saffron-500, offset 2px. This is currently not mentioned
    anywhere in theme.css; add it as a global :focus-visible rule.
  - Color is never the only signal: the severity dots, status indicators,
    and chart colors throughout this spec are paired with text labels or
    icons, not color alone (relevant for colorblind users, and for the
    spice/monsoon red-green pairing specifically, which is the single most
    common colorblind-inaccessible combination — make sure severity is
    always also readable from an icon or label, not just hue).
  - All map data must have a non-map fallback view (e.g. the ranked list
    next to the Analytics map, the table in AlgorithmLab) — never make a
    map the ONLY way to access a piece of data.
