====================================================================
DARKSTORI - ENGINEERING GAP ANALYSIS & INDUSTRY-LEVEL IMPROVEMENT PLAN
====================================================================
Prepared as a phased roadmap to convert the existing architecture
into a defensible, production-grade, resume-worthy system.

Repo: https://github.com/AadityaUniyal/Darkstori
Domain: Quick-commerce dark store intelligence (coverage gap
analysis + demand forecasting) for the Indian market.

--------------------------------------------------------------------
HOW TO USE THIS DOCUMENT
--------------------------------------------------------------------
Each phase lists:
  - GAP: what's currently missing or shallow
  - WHY IT MATTERS: the real-world engineering reason this is a gap
  - FIX: concrete, mostly-free tools/techniques to close it
  - RESUME LINE: how to phrase the completed work for a resume/interview

Phases are ordered by effort-to-impact ratio (cheapest/highest-signal
first). You do not need to do all phases before showing this project
to recruiters -- even Phase 1 + Phase 2 meaningfully changes the story.

====================================================================
PHASE 1 -- DATA & ML METHODOLOGY (cheap, fixes a real correctness risk)
====================================================================

GAP 1.1: No documented train/test split methodology for demand forecasting
WHY IT MATTERS: Demand forecasting is a time-series problem. A random
  train/test split leaks future information into training (the model
  "sees" next month while training on this month), producing inflated
  accuracy numbers that fall apart in production. This is one of the
  most common beginner mistakes in applied ML and one of the first
  things an ML interviewer will probe.
FIX: Implement walk-forward validation (a.k.a. rolling-origin
  evaluation) -- train on months 1-N, validate on month N+1, slide
  forward. scikit-learn's TimeSeriesSplit is a ready-made tool for
  this. Document the exact split logic in the README.
RESUME LINE: "Implemented walk-forward validation for demand
  forecasting models to prevent temporal data leakage, replacing a
  naive random split."

GAP 1.2: "85%+ accuracy" has no defined metric or baseline
WHY IT MATTERS: Accuracy is meaningless without knowing the metric
  (MAPE? RMSE? R^2?) and without a baseline to compare against (a
  naive "predict last week's value" baseline is standard in
  forecasting). Unqualified accuracy claims are an immediate red flag
  in technical interviews.
FIX: Report MAPE (Mean Absolute Percentage Error) and RMSE against a
  naive seasonal baseline. State this explicitly: "XGBoost model
  achieves X% MAPE vs Y% MAPE for naive baseline."
RESUME LINE: "Benchmarked demand forecasting models against a naive
  seasonal baseline, demonstrating a measurable improvement in MAPE."

GAP 1.3: No data versioning
WHY IT MATTERS: If training data changes (new scrape, updated Kaggle
  dataset) there is no way to trace which model was trained on which
  data snapshot -- makes debugging and reproducing results impossible.
FIX: Use DVC (Data Version Control, free, open-source, git-like
  workflow) to version datasets alongside code.
  Reference: https://dvc.org/doc
RESUME LINE: "Introduced data versioning with DVC to ensure
  reproducibility between model versions and training datasets."

GAP 1.4: No data validation between pipeline stages
WHY IT MATTERS: data_pipeline.py feeding training_pipeline.py without
  schema/range checks means bad data (nulls, outliers, schema drift
  from the scraper) silently corrupts model training instead of
  failing loudly.
FIX: Add a validation layer using Great Expectations (free,
  open-source) or a lightweight custom Pydantic-based schema check
  before data enters the ML pipeline.
  Reference: https://greatexpectations.io/
RESUME LINE: "Added automated data validation gates using Great
  Expectations to catch schema drift and data quality issues before
  model training."

PHASE 2 -- API / BACKEND PRODUCTION-READINESS (cheap, high credibility)
====================================================================

GAP 2.1: No circuit breaker around external API calls
WHY IT MATTERS: Calls to Google Places/Geocoding/Distance Matrix (or
  their free replacements) can be slow or fail. Without a circuit
  breaker, a single degraded external dependency can cascade and hang
  your entire request chain -- a classic production outage pattern.
FIX: Wrap all external calls (Google APIs, scrapers) with a circuit
  breaker library such as pybreaker (Python, free). Fail fast and
  return a cached/degraded response instead of hanging.
  Reference: https://github.com/danielfm/pybreaker
RESUME LINE: "Implemented circuit breaker pattern around all external
  API dependencies to prevent cascading failures under degraded
  third-party service conditions."

GAP 2.2: No API versioning
WHY IT MATTERS: Any future change to a response shape will silently
  break existing clients. Real APIs are versioned from day one
  (/api/v1/...).
FIX: Restructure routes under /api/v1/ prefix now, before it's a
  breaking change to fix later.
RESUME LINE: "Designed API with versioned endpoints (/api/v1/) to
  support backward-compatible evolution."

GAP 2.3: Latency reported only as an average ("sub-200ms average")
WHY IT MATTERS: Averages hide tail latency. A system with 150ms
  average but 3-second p99 is a bad user experience that an average
  completely conceals. p95/p99 are the metrics real engineering teams
  actually track and are what interviewers ask about.
FIX: Load test with Locust or k6 (both free, open-source) and publish
  actual p50/p95/p99 latency numbers with a graph in the README.
  Reference: https://k6.io/ | https://locust.io/
RESUME LINE: "Load-tested the API with k6, measuring and publishing
  p50/p95/p99 latency under simulated concurrent load."

GAP 2.4: No idempotency handling on prediction endpoints
WHY IT MATTERS: If a client retries POST /predictions/demand (e.g.
  due to a network blip), does it double-process or return the same
  cached result? Without idempotency keys, retries can cause
  duplicate work or inconsistent state.
FIX: Accept an idempotency key header on write/predict endpoints,
  cache the response against that key in Redis for a short TTL.
RESUME LINE: "Added idempotency-key support on prediction endpoints
  to make retried requests safe under network failure conditions."

GAP 2.5: Shallow health checks
WHY IT MATTERS: A /health endpoint that just returns 200 doesn't tell
  you if the DB, Redis, or the loaded ML model are actually healthy --
  this is the difference between "process is running" and "system is
  actually able to serve correct responses."
FIX: Split into /health/live (process up) and /health/ready (DB +
  Redis + model all reachable and loaded) -- this is the standard
  Kubernetes liveness/readiness pattern.
RESUME LINE: "Implemented Kubernetes-style liveness/readiness health
  checks verifying database, cache, and model-loading status
  independently."

PHASE 3 -- ML SYSTEMS MATURITY (medium effort, strong signal)
====================================================================

GAP 3.1: No model registry or experiment tracking
WHY IT MATTERS: joblib serialization alone can't answer "which model
  is live right now, what were its metrics, and can I roll back to
  the previous version." This is core MLOps discipline.
FIX: Use MLflow (free, self-hostable) to track experiments, metrics,
  and register models with versions.
  Reference: https://mlflow.org/
RESUME LINE: "Adopted MLflow for experiment tracking and model
  versioning, enabling comparison and rollback between model
  iterations."

GAP 3.2: No drift detection
WHY IT MATTERS: Demand patterns shift (festivals, monsoon season,
  competitor pricing changes). A model that was accurate at training
  time silently degrades in production with nothing to flag it.
FIX: Track prediction residuals against actual outcomes on a rolling
  window (weekly); alert if error exceeds a defined threshold
  (simple z-score or population stability index is enough to start).
RESUME LINE: "Built a lightweight drift-monitoring job that tracks
  prediction residuals over time and flags model degradation."

GAP 3.3: No clarity on feature computation/caching strategy
WHY IT MATTERS: "20+ features" computed how and cached where affects
  both latency and consistency. Recomputing everything per-request
  from raw DB queries at scale is a bottleneck; not caching correctly
  risks serving stale features.
FIX: Document and, if needed, implement a simple feature cache in
  Redis with explicit TTLs, or move toward a lightweight feature
  store pattern.
RESUME LINE: "Designed a Redis-backed feature caching layer to reduce
  per-request feature computation latency."

PHASE 4 -- SECURITY DEPTH (medium effort, differentiates from typical
student projects)
====================================================================

GAP 4.1: JWT with no refresh token rotation or revocation
WHY IT MATTERS: If a token is compromised, there's no way to revoke
  it before natural expiry -- a real security gap in any system
  calling itself "enterprise-grade."
FIX: Implement short-lived access tokens + refresh token rotation,
  backed by a Redis-based revocation/blacklist for compromised tokens.
RESUME LINE: "Implemented refresh-token rotation with a Redis-backed
  revocation list to support immediate token invalidation."

GAP 4.2: "Encrypted data storage" is unspecified
WHY IT MATTERS: At-rest DB encryption and field-level encryption are
  very different guarantees; an unspecified claim reads as vague to
  a technical reviewer.
FIX: Decide and document explicitly which fields get field-level
  encryption (e.g. PII) vs. relying on DB-level at-rest encryption
  (e.g. Neon/Postgres native encryption).
RESUME LINE: "Applied field-level encryption to PII fields in
  addition to database-level at-rest encryption."

GAP 4.3: No audit logging
WHY IT MATTERS: Knowing who accessed what data and when is standard
  practice for anything handling business-sensitive data, and it's a
  cheap addition most student projects skip entirely -- so it stands
  out.
FIX: Add structured audit logs (user id, endpoint, params, timestamp)
  for all authenticated write/read-sensitive endpoints.
RESUME LINE: "Added structured audit logging across authenticated
  endpoints for traceability and compliance-readiness."

PHASE 5 -- INFRA / DEVOPS PROOF (medium effort, highest credibility
gap-closer)
====================================================================

GAP 5.1: CI/CD, Docker, and monitoring are listed but not demonstrably
  running
WHY IT MATTERS: Listing "GitHub Actions, Prometheus, Grafana" in a
  tech stack table is a claim; a linked, passing CI run and a
  screenshotted live dashboard is proof. Interviewers and recruiters
  weight proof far higher than lists.
FIX:
  - Make the GitHub Actions workflow actually gate merges on tests +
    linting passing.
  - Stand up a real Grafana dashboard (request rate, error rate,
    p95 latency, prediction volume) even on a free-tier deployment.
  - Link the passing CI badge and a dashboard screenshot directly in
    the README.
RESUME LINE: "Configured CI pipeline gating merges on automated tests
  and linting; built a Grafana dashboard tracking live request rate,
  error rate, and latency percentiles."

GAP 5.2: No environment parity guarantee
WHY IT MATTERS: If local Docker Compose doesn't match what's actually
  deployed, "works on my machine" bugs are inevitable.
FIX: Use the same Docker images/Compose definitions for local dev and
  deployment (e.g. via Render/Fly.io free tier), documented explicitly.
RESUME LINE: "Ensured environment parity between local development
  and deployment using identical containerized configurations."

PHASE 6 -- CLOSE THE LOOP WITH REAL DATA (highest effort, highest
overall payoff)
====================================================================

GAP 6.1: The system has not been shown running end-to-end on live,
  current data over time
WHY IT MATTERS: This is the single biggest gap. Everything above adds
  depth to the architecture; this phase proves the system actually
  works in the real world, which is what separates "a well-structured
  student project" from "a system I can defend in a design interview."
FIX:
  - Schedule the scraper to run periodically (Celery beat / cron),
    pulling fresh data weekly.
  - Track coverage-gap analysis changes over time as real dark stores
    open/close -- show a before/after diff.
  - Backtest the demand model against weeks that have already
    happened; compare predicted vs. actual and publish the error.
  - Document real failure modes encountered (e.g. "scraper broke when
    Blinkit changed their HTML structure, added a schema-drift
    check in response") -- these real incident stories are gold in
    interviews, far more valuable than hypothetical ones.
RESUME LINE: "Operated the data pipeline on a live weekly schedule
  against real market data, backtesting demand forecasts against
  actual outcomes and resolving real scraper failures caused by
  upstream site changes."

PHASE 7 -- PROFESSIONAL / ADVANCED FRONTEND UI (free, highest visual
impact for demos and interviews)
====================================================================

GAP 7.1: Current stack (React + Recharts + Framer Motion + Zustand) is
  solid but generic -- nothing signals "advanced" or "designed," and
  Dashboard/Analytics/Predictions pages likely look like default
  component-library output.
WHY IT MATTERS: In interviews and on a resume link, the UI is the
  first thing anyone sees. A dashboard that looks like a real product
  (not a tutorial clone) massively changes the perceived quality of
  the whole project before anyone reads a line of backend code.
FIX (all free/open-source):
  - Adopt shadcn/ui (https://ui.shadcn.com/) as the base component
    layer -- it's not a traditional component library, it's
    copy-in source you own and can restyle freely, which reads as
    more "custom-built" than MUI/Ant/Bootstrap defaults.
  - Use Tailwind CSS (already compatible with your Vite/React setup)
    with a defined design token system (consistent spacing, a real
    color palette, a real type scale) instead of ad-hoc utility
    classes -- this alone is what separates "styled" from "designed."
  - For dashboard-specific components (KPI cards, stat trends, data
    tables), consider Tremor (https://www.tremor.so/) -- free,
    React, built specifically for analytics dashboards, integrates
    with Tailwind.
  - Add skeleton loading states and empty states for every data view
    (most student dashboards only show the "happy path" with data
    already loaded) -- this is a small effort, high-polish signal.
  - Add a dark mode toggle (Tailwind + shadcn support this natively)
    -- expected in "professional" dashboards now, cheap to add.
RESUME LINE: "Rebuilt the dashboard UI using shadcn/ui and Tailwind
  with a custom design system, including loading/empty states and
  dark mode support."

GAP 7.2: No real-time UI feedback -- dashboard likely requires manual
  refresh to see new data
WHY IT MATTERS: An "intelligence platform" that doesn't update live
  undercuts its own pitch. Real-time UI is also one of the more
  technically interesting things to discuss in an interview.
FIX: See Phase 8 below (live database) -- pair it with:
  - React Query (already in your stack) configured with
    refetchInterval or, better, driven by WebSocket/SSE push instead
    of polling.
  - Toast notifications (e.g. via shadcn's toast/sonner) when new
    data arrives (e.g. "3 new dark stores detected in Delhi NCR").
RESUME LINE: "Added real-time UI updates via WebSocket push,
  replacing manual refresh with live toast notifications on new data."

PHASE 8 -- LIVE DATABASE & REAL-TIME CONNECTIONS (free tiers, genuine
production pattern)
====================================================================

GAP 8.1: Current setup (Neon Postgres + Redis cache, presumably
  polled by the frontend) has no real-time data path
WHY IT MATTERS: "Real-Time Business Intelligence" is listed as a
  feature in the README, but a request/response REST API polled
  periodically is not real-time -- it's just frequent polling. Real
  real-time means the server pushes updates to connected clients.
FIX (free options, ranked by fit):
  - Best free option: Supabase (https://supabase.com/) -- free-tier
    Postgres with built-in Realtime (listens to Postgres row changes
    via logical replication and pushes them over WebSockets to
    subscribed clients) plus built-in auth and storage. This could
    either replace Neon entirely or run alongside it if you want to
    keep Neon for the ML/analytics side and use Supabase Realtime
    purely for the live feed layer.
  - Alternative: keep Postgres (Neon) as-is and add a lightweight
    WebSocket layer yourself using FastAPI's native WebSocket support
    (no extra service needed) -- broadcast events when new stores/
    predictions are written to the DB. More manual, but keeps your
    current DB choice and is a strong "I built this myself" story.
  - For ML prediction jobs specifically: use Celery (already in your
    stack) to push a WebSocket event when a prediction job completes,
    instead of the frontend polling a job-status endpoint.
RESUME LINE: "Integrated Supabase Realtime (Postgres logical
  replication over WebSockets) to push live coverage and demand
  updates to connected clients without polling."
  -- or, if self-built --
  "Built a custom WebSocket broadcast layer in FastAPI to push live
  database change events to the frontend, replacing polling."

GAP 8.2: No connection pooling visibility / resilience for the DB
  layer under real concurrent load
WHY IT MATTERS: SQLAlchemy connection pooling is mentioned as a
  feature, but there's no evidence of it being tuned or tested under
  load -- a common real failure mode is exhausting the connection
  pool under concurrent WebSocket + REST traffic.
FIX: Explicitly configure and document pool_size/max_overflow for
  SQLAlchemy, and include this in your Phase 2 load testing (k6/
  Locust) so you can show the system holds up under concurrent
  REST + WebSocket load, not just REST alone.
RESUME LINE: "Tuned and load-tested database connection pooling to
  sustain concurrent REST and WebSocket traffic without exhaustion."

PHASE 9 -- REPLACING THE MAP LAYER (free, but visually and
technically upgraded from basic Leaflet)
====================================================================

GAP 9.1: Current map (Leaflet + presumably default OSM raster tiles)
  looks and feels dated compared to modern product maps
WHY IT MATTERS: For a geospatial intelligence product, the map *is*
  the product's face -- a flat, default-styled Leaflet map with raster
  tiles reads as "tutorial project," even if the underlying geospatial
  logic (coverage gaps, clustering) is genuinely sophisticated.
FIX -- ranked options, all free at your project's scale:

  OPTION A (recommended): MapLibre GL JS
    https://maplibre.org/
    - Fully free, open-source fork of Mapbox GL JS (no API key, no
      usage limits, no vendor lock-in).
    - Renders vector tiles (not raster images) -- smooth zooming,
      3D tilt/rotation, much closer to a "modern SaaS product" feel
      than Leaflet's raster tiles.
    - Supports custom, professional-looking map styles (dark mode
      map, custom color-coded coverage overlays) via free style
      JSON -- use OpenFreeMap (https://openfreemap.org/) or
      Protomaps (https://protomaps.com/) for completely free vector
      tile hosting with no usage caps, no signup required for
      OpenFreeMap.
    - Directly supports heatmap layers, clustering, and choropleth-
      style fill layers natively -- fits your coverage-gap and
      demand-density visualization needs better than Leaflet plugins.
    - React wrapper available: react-map-gl
      (https://visgl.github.io/react-map-gl/) works with MapLibre.

  OPTION B: deck.gl (https://deck.gl/) layered on top of MapLibre
    - Built by the Uber Vis team, free/open-source, purpose-built for
      large-scale geospatial data visualization (exactly your 4,400+
      store use case) -- supports GPU-accelerated hexbin/heatmap/
      arc layers that would make coverage-gap and demand visualizations
      look genuinely advanced.
    - Higher learning curve than plain MapLibre, but this is the
      kind of library real geospatial/data-viz teams use in production,
      so it's a strong differentiator if you have the time budget.

  OPTION C (data source only, pairs with A or B): switch geocoding/
    places data from Google APIs to free OSM-based sources -- keeps
    everything in the same free/open ecosystem as MapLibre:
    - Nominatim (https://nominatim.org/) -- free geocoding
    - Overpass API (https://overpass-api.de/) -- free POI/places data
    - OSRM (https://project-osrm.org/) -- free routing/distance matrix

  RECOMMENDATION: Migrate to MapLibre GL JS + OpenFreeMap vector
  tiles (Option A) as the baseline -- it's a drop-in-scale effort
  compared to Leaflet, free with no usage caps, and immediately
  changes the visual quality of the dashboard. Add deck.gl layers
  (Option B) specifically for the heatmap/coverage-density views if
  you want the more advanced geospatial-viz story.

RESUME LINE: "Replaced Leaflet raster-tile maps with MapLibre GL JS
  and free vector tile hosting (OpenFreeMap), adding GPU-accelerated
  heatmap and clustering layers via deck.gl for coverage-gap
  visualization."

SUGGESTED PRIORITY ORDER (effort vs. resume impact)
====================================================================
1. Phase 1 (walk-forward validation + honest metrics)   -- cheap, fixes
   a real correctness risk, high interview credibility.
2. Phase 2 (circuit breaker + real load testing)          -- cheap,
   very high "production-minded engineer" signal.
3. Phase 9 (MapLibre + free vector tiles)                  -- cheap
   to medium effort, highest immediate visual payoff for demos.
4. Phase 7 (shadcn/ui + Tailwind design system polish)     -- medium
   effort, changes first impressions of the whole project.
5. Phase 3 (MLflow model registry + drift monitoring)     -- medium
   effort, strong "understands ML systems" signal.
6. Phase 8 (Supabase Realtime / WebSocket live updates)    -- medium
   effort, makes the "real-time intelligence" pitch actually true.
7. Phase 5 (real CI + real dashboard screenshots)          -- medium
   effort, closes the "claims vs proof" gap.
8. Phase 4 (security depth)                                -- medium
   effort, differentiates from typical student projects.
9. Phase 6 (live data loop)                                 -- highest
   effort, highest overall payoff -- do this last once the
   foundations above are solid.
